# پرتال فروش عمده‌ی مَن (Man B2B Portal)

پرتال سفارش و حساب‌وکتاب برای نماینده‌ها/پخش‌کننده‌ها، فروشگاه‌ها، مشتریان سازمانی و آزمایشگاه‌ها، به همراه پنل مدیریت برای مدیر فروش، کارشناسان فروش و ادمین.

| لایه | فناوری |
|---|---|
| بک‌اند | Django 5.1 + Django REST Framework، JWT، PostgreSQL 16 |
| صف و کش | Celery (صف‌های جدا: notifications، integrations، reports) + Redis (کش و بروکر جدا) |
| فرانت | Next.js 14 (App Router)، TypeScript، Tailwind، راست‌به‌چپ، فونت وزیرمتن، تم کرم و آبی نیمه‌تیره، PWA |
| زیرساخت | Docker، Nginx (rate-limit و صف درخواست)، PgBouncer، استقرار blue-green با rollback خودکار، GitHub Actions |

---

## نقش‌ها و دسترسی

| نقش | چه چیزی می‌بیند |
|---|---|
| ادمین کل | همه‌چیز + کاربران سازمان + اجرای دستی همگام‌سازی حسابداری |
| مدیر فروش | تأیید مشتری‌ها، همه‌ی سفارش‌ها، قیمت‌گذاری، محصولات، اعتبار، گزارش‌ها |
| کارشناس فروش | فقط مشتری‌ها و سفارش‌های استان‌های خودش یا مشتری‌هایی که به او سپرده شده |
| نماینده / فروشگاه / سازمانی / آزمایشگاه | قیمت اختصاصی گروه خودش، سفارش‌ها و حساب مالی خودش |
| زیرکاربر مشتری | دسترسی جدا (مثلاً حسابدار: فقط بخش مالی، بدون ثبت سفارش) |

### سمت‌ها (Positions)

ادمین در «کاربران و سمت‌ها» هر تعداد سمت تعریف می‌کند (مثلاً انباردار، حسابدار، مسئول بازاریابی). هر سمت یک چک‌لیست از ۱۷ بخش پنل دارد و یک محدوده‌ی داده: «همه‌ی مشتری‌ها» یا «فقط استان‌ها و مشتری‌های خودش». کاربری که آن سمت را بگیرد، بعد از ورود فقط منوها و صفحه‌های همان بخش‌ها را می‌بیند و API هم همان را اعمال می‌کند (`apps/accounts/perms.py`). سه سمت ادمین کل، مدیر فروش و کارشناس فروش پیش‌فرض هستند. ادمین از همان فرم می‌تواند حساب آماده‌ی مشتری (نماینده، فروشگاه، سازمانی، آزمایشگاه) هم بسازد که نیازی به تأیید ندارد. ورود کارکنان با نام کاربری و رمز یا با موبایل و کد پیامکی است.

دسترسی‌ها در بک‌اند اعمال می‌شود (`apps/accounts/scoping.py`, `apps/core/permissions.py`). منوها در فرانت فقط برای راحتی کاربر است.

## قابلیت‌ها

**فاز ۱ — فروشگاه آنلاین نماینده‌ها**
- محصول: کد کالا، عکس، دسته، تعداد در کارتن، حداقل سفارش، موجود/ناموجود، محصولات مخصوص یک نوع مشتری
- قیمت‌گذاری: گروه‌های قیمت، لیست قیمت جدا برای هر گروه (ویرایش گروهی با درصد از قیمت پایه)، تخفیف پلکانی حجمی
- ثبت‌نام و ورود با کد پیامکی، آپلود مدارک، صفحه‌ی «در انتظار تأیید» و ارسال دوباره‌ی مدرک
- صف تأیید مشتری: دیدن مدارک، تأیید یا رد با دلیل، تعیین گروه قیمت، کارشناس فروش و سقف اعتبار
- کاتالوگ با جست‌وجو، فیلتر دسته و قیمت اختصاصی، انتخاب تعداد به کارتن
- سبد و ثبت سفارش: آدرس تحویل، توضیحات، پیش‌فاکتور PDF فارسی، «تکرار سفارش قبلی»، جلوگیری از ثبت دوباره (Idempotency-Key)
- پیگیری سفارش: ثبت ← تأیید ← آماده‌سازی ← ارسال ← تحویل، با پیامک در هر مرحله
- صف سفارش‌ها (ادمین): تغییر وضعیت، ویرایش اقلام با محاسبه‌ی دوباره، یادداشت داخلی، فیلتر شهر/استان/کارشناس
- کیت بازاریابی: پوستر، بنر، عکس، ویدیو، دسته‌بندی بر اساس کمپین
- داشبورد مشتری: آخرین سفارش‌ها، اطلاعیه‌ها، دسترسی سریع، وضعیت اعتبار

**فاز ۲ — حساب‌وکتاب و داشبورد مدیران**
- اتصال به حسابداری (`apps/integrations`): همگام‌سازی محصول/موجودی/قیمت هر ۱۵ دقیقه، ارسال خودکار سفارش پس از تأیید (با تلاش مجدد)، دریافت فاکتور و ثبت در حساب مشتری. آداپتور `rest` برای یک bridge در کنار سپیدار/هلو/همکاران و آداپتور `mock` برای توسعه.
- حساب مالی: سقف اعتبار، اعتبار باقی‌مانده، مانده بدهی، معوق، گردش حساب با مانده‌ی لحظه‌ای، صورت‌حساب دوره‌ای PDF
- چک‌ها: ثبت با تصویر، وضعیت در جریان/وصول/برگشتی (ثبت خودکار در حساب)، یادآوری پیامکی ۳ روز قبل از سررسید
- پرداخت آنلاین: درگاه زرین‌پال (و درگاه آزمایشی)، تسویه یا پیش‌پرداخت سفارش
- آرشیو فاکتورها و دانلود
- کنترل اعتبار: سقف اعتبار هر مشتری، مسدود شدن سفارش وقتی اعتبار تمام شده (با قفل ردیف برای جلوگیری از سفارش‌های هم‌زمان)
- داشبورد مدیران: نمودار فروش روزانه/هفتگی/ماهانه (شمسی)، تفکیک شهر، محصول، نماینده و کارشناس، نماینده‌های غیرفعال، مطالبات معوق، خروجی اکسل
- زیرکاربرها برای شرکت مشتری

**فاز ۳ — انگیزه، پشتیبانی و بازار آزمایشگاهی**
- هدف فروش ماهانه، نوار پیشرفت، پاداش پلکانی، رتبه‌بندی نماینده‌ها
- مرجوعی و شکایت با عکس و وضعیت رسیدگی
- تیکت پشتیبانی به کارشناس فروش، پشتیبانی یا مالی
- نقشه‌ی پوشش شهرها (دارای/بدون نماینده) و صف درخواست‌های نمایندگی؛ فرم عمومی `/agency` و API `POST /api/v1/agency-applications/` برای سایت شرکت
- آموزش: دوره، ویدیو، آزمون کوتاه
- پرتال آزمایشگاهی: کیت‌های بیوشیمی و هماتولوژی با مستندات فنی و بروشور
- نسخه‌ی موبایل PWA: نصب روی گوشی، کش پوسته‌ی برنامه، اعلان (Web Push)

## اجرای سریع (توسعه)

```bash
cp .env.example .env
# برای آزمایش محلی: DJANGO_DEBUG=1 و OTP_DEBUG_ECHO=1 و SECURE_COOKIES=0
docker compose up --build -d
docker compose run --rm migrate seed      # داده‌ی نمونه
# http://localhost:8080
```

بدون داکر:

```bash
cd backend && pip install -r requirements.txt
DJANGO_DEBUG=1 CELERY_TASK_ALWAYS_EAGER=1 python manage.py migrate
DJANGO_DEBUG=1 python manage.py seed_demo
DJANGO_DEBUG=1 CELERY_TASK_ALWAYS_EAGER=1 python manage.py runserver
cd ../frontend && npm ci && BACKEND_INTERNAL_URL=http://localhost:8000 npm run dev
```

## پایداری زیر بار

- **Nginx**: محدودیت نرخ برای هر IP (API و ورود جدا)، صف کردن burst به جای رد کردن، تلاش دوباره روی نسخه‌ی سالم دیگر، کش فایل‌های استاتیک
- **Gunicorn** با worker‌های threaded و بازیافت دوره‌ای؛ چند replica از بک‌اند و فرانت
- **PgBouncer** (transaction pooling) جلوی PostgreSQL تا هزاران اتصال هم‌زمان پایگاه‌داده را از کار نیندازد
- **Redis جدا** برای کش (LRU) و صف (بدون eviction، با AOF) تا پر شدن کش صف کارها را پاک نکند
- **Celery** با صف‌های جدا، `acks_late` و تلاش مجدد نمایی؛ کارهای کند (پیامک، حسابداری، گزارش) خارج از مسیر درخواست کاربر
- **کش**: داشبورد مدیران ۲ دقیقه، لیست استان‌ها ۱ ساعت؛ اگر Redis قطع شود سایت بدون کش ادامه می‌دهد
- **یکپارچگی داده**: قفل ردیف مشتری هنگام ثبت سفارش، شماره‌ی سفارش از sequence پایگاه‌داده، `Idempotency-Key` برای سفارش و پرداخت
- **Throttling** در DRF (OTP، ورود، ثبت سفارش)
- **Health check**: `/api/v1/health/live/` و `/api/v1/health/ready/` (پایگاه‌داده و Redis)
- تست بار: `deploy/loadtest/k6.js`

## استقرار و Rollback امن

```
deploy/
  docker-compose.infra.yml   پایگاه‌داده، PgBouncer، دو Redis، Nginx — یک‌بار اجرا می‌شود
  docker-compose.app.yml     یک «رنگ» از برنامه (blue یا green)
  scripts/deploy.sh <TAG>    استقرار بدون قطعی
  scripts/rollback.sh [TAG]  بازگشت فوری به نسخه‌ی قبل (یا هر نسخه‌ی دلخواه)
  scripts/backup.sh          پشتیبان فشرده از پایگاه‌داده
  scripts/restore.sh <file>  بازگردانی پشتیبان (آخرین راه‌حل)
```

مراحل `deploy.sh`:
1. پشتیبان‌گیری از پایگاه‌داده
2. دریافت ایمیج‌های برچسب‌خورده با SHA کامیت (ایمیج‌ها تغییرناپذیرند)
3. اجرای migration‌ها (فقط افزایشی؛ ستون حذف‌شده یک انتشار بعد پاک می‌شود، پس نسخه‌ی قبلی هم با schema جدید کار می‌کند)
4. بالا آوردن رنگ جدید کنار رنگ فعلی
5. صبر تا آماده شدن (`/health/ready`)
6. smoke test
7. تغییر upstream در Nginx با `nginx -s reload` (درخواست‌های در جریان قطع نمی‌شوند)
8. انتقال زمان‌بند Celery beat (فقط یکی فعال است)
9. پایش رنگ جدید تا `ROLLBACK_GRACE` ثانیه؛ اگر سلامت از دست برود rollback خودکار. رنگ قبلی تا پایان این مدت روشن می‌ماند تا rollback در چند ثانیه انجام شود.

اگر هر کدام از مراحل ۱ تا ۶ خطا بدهد، ترافیک اصلاً جابه‌جا نمی‌شود.

GitHub Actions:
- `ci.yml`: تست‌های بک‌اند روی PostgreSQL و Redis واقعی، بررسی همگام بودن migration‌ها، typecheck و build فرانت
- `deploy.yml`: ساخت و push ایمیج‌ها به GHCR و استقرار روی سرور با SSH؛ گزینه‌ی `rollback` یا انتخاب یک `tag` قدیمی

Secrets مورد نیاز در GitHub Environment: `DEPLOY_HOST`، `DEPLOY_USER`، `DEPLOY_SSH_KEY`. روی سرور، مخزن در `/opt/man-portal` و فایل `.env` در ریشه‌ی آن قرار می‌گیرد.
